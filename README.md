# Humanizer-zh

**去掉中文里的套话，保留你想说的话。**

“在当今快速发展的时代”“这不仅是一次更新，更是效率的飞跃”“让我们拭目以待”——如果一篇稿子删掉这些话，内容一点没少，它们大概就可以删了。

Humanizer-zh 是一个中文编辑 skill，用来处理空话、重复和生硬句式，保留事实、语气和作者立场。给能读取 `SKILL.md` 的 Agent 一份原稿，就可以开始编辑。文章、README、工作邮件、产品介绍和技术文档都可以用。

## 先看一段

下面是演示文稿中的更新说明。

**改写前**

> 新的软件更新充分彰显了团队对创新的持续追求。这不仅是一次更新，更是效率的飞跃。它新增 CSV 导出、全文搜索和批量重命名。离线编辑计划在下一版推出，目前尚未完成测试。部分试用者认为搜索更快，但团队还没有测量数据。

**改写后**

> 这次更新新增 CSV 导出、全文搜索和批量重命名。离线编辑计划在下一版推出，目前尚未完成测试。部分试用者觉得搜索更快，但团队还没有测量数据。

删去两句宣传，三个功能还在，离线编辑仍是计划，搜索变快仍是试用者的感受。

## 直接试用

克隆仓库：

```bash
git clone https://github.com/liushuchun/antiAIstyle.git humanizer-zh
cd humanizer-zh
```

在这个目录里打开能读取本地文件的 Agent，发送：

```text
请读取当前目录的 SKILL.md，按它的规则润色下面这段中文。
保留事实、限定条件和我的语气，只输出改写稿。

【粘贴原文】
```

也可以把 `SKILL.md` 和 `references/` 一起安装到所用 Agent 的本地技能目录，按该工具支持的方式调用 `humanizer-zh`。请保留目录关系，案例文件通过相对路径加载。

改写由你使用的 Agent 和模型完成，无需为本仓库单独配置 API Key。

## 按你的稿子来改

轻改一封邮件：

```text
按 humanizer-zh 润色下面的邮件。只改别扭和重复的句子，
保留称呼、感谢和原来的礼貌程度，不改变承诺或时间安排。
```

改一篇 README：

```text
按 humanizer-zh 修改 README.md。让用途和上手方法更容易找到，
删去空泛宣传。允许调整标题和段落顺序，检查相关锚点与链接；
保留命令、路径、功能限制，不补写未经验证的效果。
```

保留自己的文风：

```text
按 humanizer-zh 润色目标文本，参考样本的句长、用词和叙述节奏。
只借鉴表达习惯，不把样本里的经历或观点写进目标文本。

【作者样本】
……

【目标文本】
……
```

只想知道哪里有问题，也可以要求“只审阅，给出具体修改建议，先不要改文件”。

## 同一篇稿子，适配不同平台

指定平台后，skill 会按内容载体调整组织方式，保留原稿的事实、限定和作者声音：

| 平台与载体 | 编辑重点 |
| --- | --- |
| 小红书图文笔记 | 尽早交代具体需求和已有体验，段落方便浏览，说明适用条件与不足。 |
| 公众号文章 | 保持文章衔接，按论述、叙事或教程展开，保留必要解释。 |
| 知乎回答、文章 | 回答紧扣题目，文章围绕议题；把判断、理由、来源与适用边界讲清楚。 |
| B站口播、专栏、动态、简介 | 口播按听懂来改，专栏保留文章结构，动态突出消息，简介对应实际视频内容。 |

例如，想把一篇原稿改成四个版本：

```text
按 humanizer-zh 把下面的原稿分别改成：
小红书图文笔记、公众号文章、知乎专栏文章、B站口播稿。
允许重组正文，保留每版的事实、条件、来源与不确定性。
沿用作者语气，本次只交付四版正文。

【原稿】
……
```

只需要单个平台时，写明“按小红书图文笔记润色”或“改成B站口播稿”即可。原稿有个人风格，就保留它；平台适配不会默认补上“姐妹们”“谢邀”或“一键三连”。具体取舍和同稿对照见 [平台适配策略](references/platforms.md)。

## 编辑时看什么

规则覆盖 [31 类表达模式](references/patterns.md)：假对比、戏剧性短句、强凑三段式、意义拔高、客服腔，以及中文里层叠的“的”、冗长的“进行”等。每类都附有前后对照和应当保留的例子。

命中一个词不等于需要修改。“闭环”可以是工程术语，破折号可以承载解释，三项列表也可能恰好就是三个功能。编辑要看它们在句子里有没有用。

几个尤其重要的边界：

| 原稿中的内容 | 编辑要求 |
| --- | --- |
| “可能有效”“供应商声称” | 保留不确定性和归因，不能改成已验证结论。 |
| 作者的态度、幽默和犹豫 | 保留有意义的表达，不统一改成中性说明。 |
| 技术术语、操作步骤、正式措辞 | 根据文体判断，不强行口语化。 |
| 代码、命令、链接目标、数据和直接引语 | 默认保护；调整范围以用户要求为准。 |
| 本来就通顺的句子 | 可以原样保留。 |

效果需要结合原稿和模型输出判断。这个项目不判断文章是否由 AI 撰写，也不承诺通过 AI 检测器。

## 仓库里有什么

```text
.
├── SKILL.md                    核心规则、文体取舍与交付检查
├── references/
│   ├── patterns.md             31 类模式、对照案例与参考来源
│   └── platforms.md            平台与载体策略、同稿适配示例
├── tests/
│   ├── fixtures/cases.json     文本编辑案例
│   ├── fixtures/structure.md   Markdown 结构保护样本
│   └── check_structure.py      受保护内容的对照检查
└── LICENSE
```

修改规则后，可以用 [测试说明](tests/README.md) 中的案例检查是否丢失条件、改变立场或补造信息。文件编辑还可以运行：

```bash
python3 tests/check_structure.py tests/fixtures/structure.md /path/to/edited-copy.md
```

先让 Agent 润色结构样本的副本，再把副本路径替换到命令中。脚本比较 YAML、代码、标题等受保护内容，内容是否忠实仍需对照原文检查。
